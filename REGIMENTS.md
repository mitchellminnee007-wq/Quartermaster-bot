# Regiment registration and role synchronization

## Existing project and storage

This is the existing Node/CommonJS discord.js bot. Existing feature JSON files and configuration remain in place. The new versioned `data/regiments.json` extends that storage convention; no SQL database or regiment registry existed in this checkout. A missing file initializes an empty registry on its first mutation. Malformed/unknown-version data fails closed and is never silently reset. Records contain UUID, name/tag, source guild, commander, source role mappings, status, registration date, sync health and seen users. The same atomic snapshot contains the grant journal and audit log.

Only one bot process may own this data file. Existing PM2 runs in single-instance fork mode; do not enable cluster mode or multiple replicas. The serialized job queue prevents in-process races. Writes use a same-directory temporary file, fsync and rename. Keep the data directory on persistent local storage on the VPS; retain backups. JSON storage is intended for this bot's existing deployment, not multi-host concurrent writers.

## Commands

- `/create-regiment name tag [member] [officer]` in the source server: Manage Server; selected roles must belong to that guild and cannot be everyone, managed or identical. Names/tags are case-insensitively unique. The caller is recorded as the proposed commander. New records start as pending_approval and contribute no LOL roles until the two-level officer/regiment vote approves the application after 48 hours. Existing active registrations remain active.
- `/delete-regiment name`: commander or coalition administrator, confirmed by an exact `ACCEPT` modal. Authorization is checked again on submission. Deleting registrations stop contributing immediately. Cleanup retries until successful; only then is the registration removed. Other regiment entitlements remain.
- `/regiment-settings [name] [member] [officer] [resync]`: readable by members; changes require commander or coalition admin, and role mapping changes must be made in the source guild. Reinvited suspended registrations can be resumed using resync by a commander/admin who also has Manage Server in the source guild.
- `/regiment-status [name]`: configuration, registration state, last successful full sync and errors.
- `/rolesync [scope] [name]`: without scope, displays the three controls; use it in the existing #rolesync channel. User scope only affects the caller. Regiment scope requires commander, source server Manage Server or coalition admin. In LOL, provide the regiment name. Coalition scope only works in LOL for its administrators or the existing bot-admin role; intended once per war, with no invented war counter or hard limit.
- `/info category`: Getting Started, LOL and Commands. Existing `/invite` provides the existing bot OAuth link. No OAuth scope, portal setting or privileged intent has been changed. The existing LOL #rolesync channel was verified read-only as 1563207553687748779. No controls were present in its latest 30 messages; use /rolesync there to display the three controls. Regiment Role Sync asks for a registered name so it also works from LOL. No old panel was overwritten. The user-provided LOL join link is https://discord.gg/8ew5AEq5x9 . It was verified through the public Discord invite API against LOL guild 1521261614484033728 (Legion of Loyalists), without joining. Contact @BravoMike185 for help.

Coalition IDs reuse `utils/roleIds.js` and the existing allied target guild from welcome.js. Automatic synchronization reacts to source roles, membership changes, target joins, role deletion and bot removal. Only active registrations contribute roles; pending and rejected applications never contribute roles. Retries and recovery run at startup and every five minutes. A fresh deployment with no registrations/grants does not perform a startup coalition sweep. Regiment sweeps include source members and historically observed users so departing members are handled without touching unrelated users.

## Safety and recovery

The desired coalition roles are the union across active regiments. A missing source member is accepted only for Discord Unknown Member (10007); access/network errors stop that user's reconciliation. A missing mapping fails closed. Guild removal suspends registrations. Deleted legacy-source registrations remain disabled for legacy verification so it cannot accidentally recreate the removed access.

The journal records grant intent before the Discord API call. Retried adds/removes are idempotent. Removal only concerns roles in the journal, never all member roles. Existing roles not granted by this subsystem are intentionally not adopted or revoked: their provenance cannot safely be inferred. Legacy fixed-source verification remains available for unregistered sources; registered sources use the new mapping instead. Per-regiment cosmetic legacy roles are not created or managed by the new registry.

There is no distributed transaction across Discord and disk: registration/settings/deletion state is committed first, failures are recorded, and retries converge. Deleting records remain until cleanup succeeds. Avoid manually editing the journal while the bot is running. On an invalid database, stop the bot and restore a verified backup. Audit entries include timestamp, actor user/server where applicable, action and subject/error; automatic actions use a null system actor. Audit covers registration, deletion, mapping changes, manual sync, sync failures and unauthorized new commands. Back up and monitor file growth; audit retention is not silently truncated.

## Democratic admission: officers, then regiments

The user-confirmed policy is a 48-hour vote. Forum `1521502333312434288` (coalition-votes) contains one officer-voting post per application. Text channel `1563235001120858122` (vote) contains its coalition overview. Both belong to LOL `1521261614484033728`. They represent one persisted poll, not two independent votes. No direct admin-approval path remains.

Each eligible regiment's individual officers vote yes/no. A user explicitly chooses the represented regiment in a modal, including when holding officer roles in multiple regiments. The first ballot is immutable and stored by application + regiment UUID + user ID; repeated clicks cannot add votes. After 48 hours, a strict majority among the ballots actually cast inside a regiment yields its one yes/no result. A tie or zero ballots yields no yes. The application is accepted only if strictly more than 50% of ALL eligible regiments produce yes. Otherwise it is rejected. There is no early acceptance. Only the currently registered commander ID of an eligible regiment may veto during the open window, immediately and irreversibly rejecting the application. Officer or coalition-admin status alone does not grant veto or override powers. The applicant and applicant regiment cannot vote on their own admission.

Before opening, the bot snapshots all existing active regiment IDs and their Officer-role member IDs, excluding bots and the applicant regiment. This fixes coalition denominators and prevents late roster inflation. Every ballot also freshly validates membership in LOL and the represented source server, current active registration and current mapped Officer role. Leader veto uses the current registered commander ID plus actual membership. Already-validly-cast ballots remain part of the historical poll if roles subsequently change; snapshots and denominators are not silently rewritten. Existing active registrations are retained without a retroactive vote.

Both messages must be durably recorded before the poll opens. openedAt and closesAt are UTC ISO timestamps exactly 48 hours apart. Startup recovery and the existing five-minute scheduler finalize expired polls and retry publication/role synchronization. Consequently normal closure is within five minutes after the deadline, or after recovery from an outage; never before the deadline. Individual ballots and vetoes are rejected at/after the deadline even if the scheduler has not yet finalized. Terminal decisions never silently reopen.

Each destination stores its own message/thread IDs, delivered revision and error. Text sends use a stable enforced nonce; recovery searches recent bot messages by poll UUID. Forum recovery searches active and the latest 100 archived threads by the unique poll name/owner before creating another post. This reduces duplicates after an uncertain API result; exactly-once external delivery cannot be guaranteed outside those recovery windows. All copies share the same transaction-protected decision. Failed updates retry without changing the decision. No applicant DMs are sent. New applications can send the single Officer notification described below. The bot reopens an archived officer thread while a poll remains open.

Required bot channel permissions: View Channel, Send Messages, Embed Links, Read Message History; additionally Send Messages in Threads and Manage Threads in the officer forum. Both channel types and these effective permissions were verified read-only. The forum has no required tags. No OAuth scopes or portal settings were changed. The complete confirmed policy is in regimentVoting.js; optional `REGIMENT_VOTE_POLICY` in the existing LOL configuration/environment can override it, but malformed/incomplete/disabled policy fails closed. No approval-channel fallback is used.

## New-admission Officer notification
New applications carry an officerNotice marker from registration. Once both voting messages exist and the poll opens, a separate ordinary message in its officer forum thread mentions only LOL Regiment Officer (1521274002465751130). Explicit allowedMentions permits only that role, no users/everyone/here. Existing applications without the marker never receive retroactive pings. Cards and edits remain mention-free.

A durable reservation precedes the one send attempt; a stable enforced nonce adds Discord deduplication. Successful sends store the message ID. Retries/restarts only inspect recent messages after an uncertain outcome, never blindly resend. This provides at-most-once attempts and no duplicate notifications: strict exactly-once delivery cannot be guaranteed across a crash between disk and Discord, so an uncertain notification can be missed and remains audited. Missing role/mention permissions are audited as skipped; no permission or role-mentionability settings are changed.

## Live ballot participation
Both admission cards display unique voters (deduplicated across regiments), total regiment ballots, represented regiments and per-regiment yes/no counts with provisional leads. Existing ballots remain immutable: a repeat or attempted vote change does not create an extra person or change policy. No voter names are listed. Long per-regiment lists are bounded to Discord's embed budget with an explicit overflow notice; totals always include the full electorate. Final coalition outcomes still wait until the deadline.

Delivery calls for the same service/poll are coalesced over 150 ms and serialized. Cards re-read persistent state before rendering, record only the revision actually rendered, and repeat if a concurrent ballot made that rendering stale. Failed edits remain in persistent message lastError/revision metadata for scheduler/restart retry. All card edits disable mentions; the existing once-only new-admission notice is separate.

## Approved regiment tag roles
Future admission approvals provision a dedicated zero-permission, non-hoisted, non-mentionable tag role in LOL between PERSONEL (1521293714385801298) and OPTIONAL (1521280822378889358). Existing HUSS registration and existing similarly named roles are not adopted or migrated. Only the created role is positioned; other roles are not explicitly reordered.
Member mapping, Officer mapping or the registered commander qualifies while present in the source guild and LOL. Losing all qualifications or leaving the source removes only journal-owned entitlement; other regiment roles remain. Empty tag roles are retained when a registration is deleted.
Creation intent is persisted before the API request, and the returned role ID immediately afterwards. An uncertain response is recovered only from a matching bot-authored creation audit entry with the unique operation reason (requires existing View Audit Log access). Without proof, provisioning blocks rather than creates a duplicate. Deleted owned roles require manual recovery. Failed provisioning appears in status and retries on the existing five-minute loop. No additional Discord privileges are enabled.

## LOL nicknames
Normal synchronization uses `[TAG] Existing name` for active approved regiment members in LOL. It chooses the largest eligible regiment by unique non-bot mapped Member/Officer users and its present registered commander, not all server visitors. A tie retains the recorded selection, otherwise a stable regiment-ID ordering is used. Source rosters are fetched once per sweep.
The original nickname and full base name are persisted before mutation; rendered names fit 32 UTF-16 units without splitting surrogate pairs. User edits pause automated nickname management, and pre-existing matching prefixes are never adopted. Only a proven bot-written nickname is restored on departure. Pending API writes are reconciled against the current nickname before retry. Owner/higher roles or missing Manage Nicknames are skipped and audited without changing permissions. Nickname failures do not masquerade as role-sync failures.
